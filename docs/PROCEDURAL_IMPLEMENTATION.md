# Hidden campaign implementation

The canonical graph remains in `shared/campaign.json` and design documentation. The player entry point is now Headquarters; the graph component is retained as source for developer reference and is not imported into gameplay.

Each new campaign stores a cryptographic random 32-bit seed, independent UUID, generator version and schema version. Eight authored incident families cover service outages, latency, intermittent transport, header rejection, burst load, traffic skew, payload correctness and shared dependencies. A run encounters each family once in an adaptive seeded order, then three mixed departure inspections. Variation includes 80/100/120 requests, affected service, service duration, traffic skew, outage window, dependency target and combinations. Current architecture persists, including paid capacity, routes, retry policy, normalization, integrity reconciliation and dependency isolation. Retry attempts generate actual extra routing work; isolation confines a shared dependency outage; payload correctness is measured separately from HTTP success. This is a bounded miniature model, not a general distributed-system or cache/message-broker simulator.

The director prioritizes pressure concepts for retry-heavy systems and distribution concepts for affinity-routed systems. Future incidents, graph nodes and ending thresholds are absent from the normal UI. Previously completed content is recorded in the journal. All eight concept families are guaranteed within a run, regardless of order. Feasible repairs are checked across seed boundaries and full runs; they are test helpers, never a player-facing auto-solve.

Eight measured ending categories are implemented: the six requested categories plus Precision and Headroom. Ending evaluation uses three completed mixed workloads, correct payloads, arrivals, tail latency, resource cost, diagnostic evidence and severe-failure recovery history. A final workload may be recorded with failures; before accepting it the player can redesign and rerun. Earlier incidents require reliable and correct delivery. This allows adverse outcomes without making a failed normal mission a dead end. Ending conditions live in developer source and are not listed to players.

Schema 3 keeps up to 20 local campaigns; a new campaign archives the old one. Completed checkpoints persist; interrupted experiments restart. Import/export supports manual transfer. Schema 2's architecture and complete history are preserved as a legacy journal when entering the procedural campaign; the original v2 storage is not deleted during migration. Existing unreadable saves are protected from silent overwrite. Explicit local clearing removes the v2 and v3 game saves only.

Cloud saves are optional and unconfigured until Firebase setup. Local play does not depend on Google or Firestore. The cloud envelope stores owner, ID, schema, revision, update time and compact campaign JSON; no frames or full traces. Transactional revisions prevent stale-device overwrite. Guest-to-account migration requires an explicit keep action. Cross-device authentication and production sync remain pending a real Firebase project and the acceptance checklist in FIREBASE_SETUP.md.

All original simulation tests remain. New tests cover seeded variation, full-run curriculum, feasible solutions, persistent decisions, actual simulated ending routes, storage reload/rejection, 12 additional Python/TypeScript frame-hash parity workloads, and procedural boundary rejection. Firebase emulator tests are a separate release gate.
